## Q1 槽位注册契约的合法字段

**结论**：`ctx.slots.register(options, component)` 的 `options` 合法字段全集（被机制实际消费的）为：
`name`（必填，槽位键）、`key`（keyed 席位必填）、`id`（list 席位必填）、`select`（chain 席位必填）、`order`（list 显示排序，默认 0）、`label`（`string | (() => string)`）、`locale`（命名空间字符串，给组件 `t` prop）、`inject`（per-entry props 工厂）、`children`（声明子席位表）、`store`、`priority`（**插件不该传**：动态插件的注册会被 guard 强制覆写）。另有 `registrant` 由运行时自动打点（renderer `_register` 从 fiber 名取，:1605），插件无需传。

**inject 返回对象的到达方式**：**作为 props**。渲染时按 `组件props = { ...kit, ...entry.inject()结果, ...槽声明inject结果, ...ownerProps }` 顺序展开合并（ownerProps 最后、获胜）；inject 返回对象里的 `hooks: {…}` 子对象会被转成 `use<Name>` 选择器 Hook props，其余键原样成为普通 props。**不通过任何 ctx**（组件只拿合成后的 props，拿不到 ctx）。

要点展开：

1. **校验在 SlotCore.register**（`<asar>\dsh-client-ui-slots\lib\index.js:163-243`）：槽位必须已声明（:165），按 kind 校验必填项——keyed 要 `options.key`（:176）、list 要 `options.id`（:182）、chain 要 `options.select`（:188）；entry 只保留字段白名单 `key/id/order/label/priority` + `select/inject/children/store/locale/registrant`（:204-219）。
2. **动态插件 guard 会改写 priority**（`<asar>\dsh-cordis-client-runner\lib\client.js:275-280`）：非 chain 席位一律 `options.priority = env.allocatePriority()`，计数器从 0 递减（:393 `nextPriority = 0`、:615 `--this.nextPriority`），即动态插件每次注册拿到 -1、-2、…。语义是"priority 低者渲染/获胜"（:168 的报错提示与 root 目录 :4864 同义）。**所以插件传 `priority` 无效，`order` 才是排序抓手**。
3. **list 席位的双排序**：注册时 ledger 按 `(priority, order)` 排（ui-slots :221）；渲染时投影再按 `order ?? 0` **升序稳定排序**（renderer :1203-1218，`let list = [...rows].sort((a, b) => a.order - b.order);`）——`order` 相同的条目保持 ledger 序（动态插件因 priority 为负排在静态在树条目之前）。
4. **`label` 支持 thunk**，投影时才求值（ui-slots :27-29 `resolveSlotLabel`；panellist 的 label 投影见 sidebar :457-465）。footer.action/overlay 的 owner 不投影 label（仅存于注册表与诊断快照），但建议照传。
5. **`locale` 合法且有用**：传了就给组件注入 `t`（renderer :742-746）；在树注册普遍传（cordis :1414、sidebar :532、workbuddy `<profiles>\dsh-workbuddy-connect-community\lib\client.js:3280`）。目录条的 `registerOptions` 没列 `locale/inject`，是因为目录只列"该席位业务上有意义的"字段——机制层面两者都合法（SlotCore :214/:217 记账）。
6. **官方标准样例**（目录自带 example，runner :5489/:5696）：`ctx.slots.inject('shell.overlay', () => ctx.slots.register({ name:'shell.overlay', id:'my-entry', order:100, label:'My entry' }, () => React.createElement('div', null, 'hello')))` —— 与本插件现有写法同形。

## Q4 本插件里 rpc 怎么拿

**结论**：`ctx.connection.rpc` **直接可达，但前提是插件对象的服务声明数组含 `"connection"`**——本插件已满足（`<本插件>\lib\client.js:787` `const inject = ["slots", "connection"];`），`:793` 的 `const connection = ctx.connection;` 每次加载都在成功执行，即活证。证据链：

1. 动态插件的 ctx 是**白名单门面**：`apply` 被包成 `plugin.apply(guarded(ctx), config)`（runner :627）；门面里属性访问走 `readService(prop, true)`（:351），**要求声明**：`declared = new Set(Object.keys(ctx.fiber.inject))`（:329），未声明即 `denyRead`，报错原文（:331）：
   > "service \"connection\" is not declared by your plugin. Declare it on the plugin you return: { inject: ['connection', …], apply(ctx) { … } } — a plain `function` has no declaration site, so use the object form."
   
   （`ctx.get("connection")` 是不要求声明的可选查找，:344——但既然声明了，直接属性访问即可。）
2. 插件对象上的 `inject` 数组就是这道门的声明源：runner 注释（:597-601）"The plugin's OWN `inject` survives (**the object form's declaration is the facade's service gate**, mirroring the host sandbox reading `ctx.fiber.inject`)"。未声明服务时插件会 parked 等 `waitingFor`（:590）。
3. `connection` 服务的浏览器面在 `dsh-client-connection`：`ctx.provide("connection", handle)`（client.browser.js :1497），handle 含 `rpc`（:1443），`rpc` 来自 `transport?.rpc ?? createWebConnectionRpc(...)`（:1387）。本插件的用法是 `rpc.call(CHANNEL, method, payload)`（`<本插件>\lib\client.js:181-183`）。
4. **与 per-entry `inject` 的区别——两者不在一个层面，不是二选一**：
   - 插件对象上的 `inject: ["slots", "connection"]` = **服务声明**（门面准入 + 激活等待），没有它 `ctx.connection` 直接被拒。
   - 注册项里的 `inject: () => ({ rpc: connection.rpc })` = **per-entry props 工厂**（Q1 机制），把值送到组件 props 上。
   - **"组件里直接读 `ctx.connection.rpc`"不可行**：组件由渲染机器只以合成 props 调用（renderer :784-790），没有任何 ctx 通道。
- **哪个更稳**：保持现状组合最稳——插件级声明 `"connection"` + apply 里取一次 `const connection = ctx.connection` + 每条注册用 per-entry `inject: () => ({ rpc: connection.rpc })` 下发。理由：这是官方 example（runner :5489/:5696 形状）与全部在树 occupant（cordis :1415、chat :13362、workbuddy :3281、dshmarket :16528）一致使用的面；inject 结果按 entry 缓存（renderer :431 `rootInjectCache`、:499 起），引用稳定；组件保持纯 props，注册卸载时随 disposal 级联，无悬挂通道。

## Q5 结论与两份代码骨架

**结论**：批 1 用「**插件级 `inject: ["slots", "connection", "timer"]`（新增 `timer`，见下）+ 每条注册各自 `inject: () => ({ rpc: connection.rpc })`**」。组件内不碰 ctx（也不可行）；不引入新的状态库，开关状态用模块级迷你 store 共享。**一个硬约束**：轮询未完成数不要用 `window.setInterval`——runner 的渲染崩溃提示表明动态包里该全局被扣留并重定向（runner :682-684），要用 timer 服务的 `ctx.interval`（:1467），而 timer verbs 要求插件声明 `"timer"`（:347）。`order` 建议：footer.action 按钮 20、overlay 浮动窗 100（理由见 Q2/Q3）。

4. **动态包对 `window.addEventListener` 是否与 `window.setInterval` 一样被扣留/重定向**：只证实了 redirect 机制存在且提示文本点名 `window.setInterval`（runner :682-684），完整 `DYNAMIC_CLIENT_REDIRECTS` 表未枚举。骨架 B 因此改用元素级 pointer capture，完全绕开该问题。
